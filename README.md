## 🛠️ Pinned Projects & Deep Dives

### 🪙 1. `b-block` | Custom Blockchain Engine
A secure, custom blockchain engine written from scratch in **Go** to explore state machine replication, data persistence trade-offs, and cryptographic verification without relying on heavy external frameworks.

#### 🏗️ System Architecture
[ Block Header ] ────► Contains: PrevHash, MerkleRoot, Timestamp, Nonce
│
▼
[ Merkle Tree ] ─────► Cryptographic tree anchoring all Transactions
│
▼
[ Tx0 ] [ Tx1 ] ─────► Input/Output structures (UTXO model)


#### 🛠️ Core Engineering & Implementation
*   **Persistent Embedded Storage:** Engineered a robust transaction persistence layer utilizing **LevelDB**. Blocks and transaction states are serialized into byte arrays and written atomically to disk, guaranteeing durable ledger states across node restarts and mitigating consensus-failure corruptions.
*   **The UTXO (Unspent Transaction Output) Model:** To prevent "double-spending" without storing every user's total balance as a single mutable variable, the engine tracks explicit outputs of transactions. The LevelDB index is queried for unspent outputs belonging to a user's public key; matching items are marked as *spent*, and new *unspent* outputs are created for the recipient.
*   **Cryptographic Verification:** Every block includes a cryptographic hash generated by hashing the block's header. The header contains a reference to the **Previous Block's Hash**, tying them together unalterably. If a single bit changes in an old transaction, its block's hash changes, breaking the downstream chain.
*   *Tech Stack:* `Go`, `LevelDB`, `Cryptography`, `Merkle Trees`

### 🌊 2. `K-Fluid` | Distributed Segmented Log Broker
A high-performance, **Kafka-like** messaging broker built in **Go** designed to handle massive streams of incoming events without overwhelming system memory or hitting random disk I/O bottlenecks.

#### 🏗️ System Architecture
Incoming Stream ──► [ Active Segment: log_0002.log ] (Sequential Writes)
│
▼ (Reaches max size)
[ Rolled Segment: log_0001.log ] (Read Only)
│
▼ (Background Task)
[ Compaction Engine ] ──► Removes redundant keys


#### 🛠️ Core Engineering & Implementation
*   **Segmented Physical Files:** To prevent performance degradation and write contentions, partitions are split into **Segments**. Only one segment is "Active" (open for writes). Once it hits a specific size threshold, it is closed, becomes read-only, and a new active segment file is spawned.
*   **Sequential Disk I/O:** Because the active file is strictly append-only, the system avoids random disk seeks. It writes sequentially, which optimizes disk head movements and maximizes raw physical throughput.
*   **Log Compaction Mechanism:** A custom background thread runs compaction policies over closed segments. It strips away stale, superseded duplicate records for any given key, minimizing storage footprint while protecting immediate read throughput.
*   *Tech Stack:* `Go`, `Distributed Systems`, `I/O Multiplexing`, `Concurrent Programming`

### 🐜 3. `Babosa` | Scalable Microservices Architecture
A clean-architecture platform blueprint designed using **TypeScript** to standardize modular microservice deployment and enforce strong separation of concerns.

#### 🏗️ System Architecture
[ External Infrastructure: Express.js, PostgreSQL, Redis ]
│  (Adapters)
▼
[ Interface Adapters / Controllers ]
│  (Ports)
▼
[ Use Cases / Domain Business Logic ]
│
▼
[ Core Domain Entities ]


#### 🛠️ Core Engineering & Implementation
*   **The Dependency Inversion Principle:** Core domain entities and business use cases are completely decoupled from external frameworks. The core defines abstractions (Ports), and infrastructure details (like Postgres or Express) implement them (Adapters), enabling seamless database swaps and straightforward unit testing.
*   **Distributed Tracing & Context Passing:** Built-in mechanisms handle unique tracing tokens across service layers, ensuring that requests jumping across independent microservice containers remain fully traceable under unified logs.
*   **State & Cache Optimization:** Implements pre-configured **Redis** layers directly into the interface adapters to intercept read requests for hot-path data, shielding downstream databases from unnecessary query overhead.
*   *Tech Stack:* `Node.js`, `TypeScript`, `Docker`, `Redis`, `golang`
